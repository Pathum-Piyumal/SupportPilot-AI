SupportPilot AI — Project Proposal
Project type: Industry-oriented AI/ML internship portfolio capstone
Version: 1.0 | Prepared: 2026-11-16
Duration: 12 weeks (target 12–15 hours/week; ~144–180 hours)
Proposed team: One undergraduate developer acting as product owner, software engineer, ML engineer, and QA, using lightweight professional team practices
Status: Proposed (all capabilities and outcomes are planned, not yet delivered)
1. Executive summary
SupportPilot AI is a human-in-the-loop customer support intelligence platform for a fictional banking support organization. It combines supervised machine learning for customer inquiry intent classification with retrieval-augmented generation (RAG) to draft evidence-grounded responses from approved demonstration policy documents. Human support agents remain responsible for reviewing and approving drafts. A full-stack web app provides a ticket inbox, classifications, referenced knowledge, drafting workflow, and operational metrics.

The aim is an industry-relevant portfolio project demonstrating Python, data preparation, scikit-learn, NLP, FastAPI, PostgreSQL, React/TypeScript, embeddings, LLM safety, tests, and repeatable deployment.
2. Problem and motivation
Customer support teams must triage messages and locate accurate policy guidance. Manual classification and policy searching can be inconsistent and time-consuming. Uncontrolled generative responses can invent policies. The proposed system provides a structured ticket workflow, ML-assisted categorization, evidence retrieval, and editable response suggestions with clear human oversight.
3. Proposed solution
A simulated support agent enters or imports a synthetic customer request; an ML classifier predicts a BANKING77 intent, recording model version and confidence. The system retrieves relevant paragraphs from demo policy documents; an LLM writes a draft linked to verifiable passages and clearly signals missing evidence. An authorized agent edits/approves or rejects the draft; the application logs the event and shows aggregate analytics.

Important boundary: This is a demonstration system, not real banking software. It must not connect to customer accounts, access credentials, process transactions, send automatic messages, or present fabricated policy content as authentic banking policy.
4. Target users and stakeholders
- Support Agent: Reviews tickets, predictions, evidence, and draft responses.
- Support Supervisor: Views aggregate volume, quality and review outcomes; manages agent access if implemented.
- Knowledge Admin: Uploads/version-controls approved demo policies.
- Developer/ML Maintainer: Runs experiments, evaluations, regression checks, releases and monitoring.
- Portfolio reviewer: Can reproduce the project and observe the complete workflow using demo data.

ML integrity	Reproducible BANKING77 training, validation, single final test evaluation, published metrics and failure analysis
ML relevance	Baseline comparison and calibration/abstention analysis; no claimed predetermined accuracy
RAG grounding	Evaluation dataset with answerable and unanswerable cases; verifiable citations; unsupported questions handled safely
End-to-end usability	Demo ticket can be created, classified, cited draft generated, edited and approved/rejected

Release gates: Weeks 1–4 ML research; Weeks 5–8 working integrated ML app; Weeks 9–10 RAG and review controls; Weeks 11–12 reproducibility and portfolio release.
6. Scope
In scope (MVP)
1. Login and two roles: agent and admin (demo accounts only).
2. CRUD-lite tickets and status workflow; pagination and filters.
3. BANKING77 intent classification with confidence, model version, and low-confidence review state.
4. Approved fictional policy document ingestion, indexing and citation-based RAG answer drafting.
5. Human editing, approval, rejection and audit trail.
6. Lightweight dashboard with ticket and review metrics, including clear distinction between business metrics and offline ML metrics.
7. Tests, CI, Docker Compose, docs and demonstrable setup.
Out of scope
Production bank integrations, customer PII, transfers/refunds/payments, automatic outbound messages, SLA prediction (no supporting labels), 24/7 infrastructure, Kubernetes, complex multi-agent autonomy, full CRM, real fine-tuned large language models, guaranteed legal/financial compliance.
7. Suggested solution architecture
```mermaid
flowchart TD
    UI[React + TypeScript app] --> API[FastAPI REST API]
    API --> AUTH[Auth / RBAC]
    API --> TICKETS[Ticket & Review Services]
    API --> ML[Intent Inference Service]
    API --> RAG[RAG Orchestrator]
    TICKETS --> DB[(PostgreSQL)]
    AUTH --> DB
    ML --> ART[Versioned sklearn Pipeline]
    RAG --> VEC[(PostgreSQL + pgvector)]
    RAG --> LLM[Configurable LLM provider]
    INGEST[Document ingestion job] --> VEC
    TRAIN[Offline BANKING77 Training + MLflow] --> ART
```
Deploy as a modular monolith, not microservices. Offline training and document indexing are separate commands/tasks rather than operations performed during HTTP requests. Use PostgreSQL for application data and pgvector for retrieval. Use a local/dev RAG provider abstraction with explicit cost ceilings.

9. Risks and controls
Risk	Impact	Mitigation
BANKING77 lacks real ticket lifecycle labels	Invalid SLA, priority or time-saving claims	Use only intent labels for supervised learning; synthetic ticket workflow for UI
RAG makes up policy details	Misleading demo	Use fictional policies, passage citations, unsupported-answer abstention, human approval
Classifier confidently misclassifies	Misrouting	Confidence calibration, threshold tuned on validation, agent override and logging
Third-party LLM downtime/cost	Broken demo	Provider interface, capped retries/tokens, mock provider for tests and fallback
Prompt injection in uploaded content	Unsafe responses	Treat documents as untrusted data, fixed instructions, tool restrictions, output validation
Data leakage or invalid ML evaluation	Untrustworthy results	Split discipline, train-only fitting of TF-IDF, untouched test set, model card
12-week scope overrun	Incomplete application	Explicit MVP gate by Week 8, optional features postponed
Exposing demo secrets/API keys	Security and cost	Environment variables, secrets scanning, restricted access, no keys in frontend


10. Project governance
Use GitHub Issues with unique IDs, acceptance criteria and statuses Backlog → Ready → In Progress → Review → Done. Work in 1-week iterations. Maintain a short weekly log, architecture decision records (ADRs), demo screenshots and a decision/risk register. Every merged change should have tests for its most important behavior and an updated user-facing document when appropriate.

Definition of Done: criteria satisfied; tests green; typed/validated API; migration reviewed if schema changed; security implications considered; README/API docs updated; no hard-coded credentials; demo path unaffected.
